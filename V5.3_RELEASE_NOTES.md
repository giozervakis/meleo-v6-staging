# MELEO v5.3 — Secure Object Storage

## What changed

Verification documents are no longer tied to a shared Docker filesystem in production. The relational API now uses a storage abstraction with two drivers:

- `local` — encrypted filesystem objects for development and backwards-compatible local testing.
- `s3` — private S3-compatible object storage for production horizontal scaling.

Files remain application-encrypted with AES-256-GCM before leaving the API process. The object store therefore receives ciphertext, not the original PDF/JPG/PNG/WEBP bytes.

## Security model

- Production startup fails unless `STORAGE_DRIVER=s3` and all S3 credentials/configuration are present.
- Verification objects use non-public keys such as `verification/YYYY/MM/doc_....bin`.
- Admin downloads are decrypted only inside MELEO after authorization.
- Admins can request a short-lived HMAC-signed document URL (default 120 seconds, hard maximum 300 seconds).
- Signed responses use `Cache-Control: no-store, private`.
- Failed DB metadata inserts trigger best-effort object cleanup to avoid orphaned uploads.

## Provider compatibility

The implementation speaks S3 Signature V4 directly using Node 22 native `fetch`; no cloud-provider SDK is required. It is intended for AWS S3 and S3-compatible providers such as MinIO or Cloudflare R2. Configure the provider endpoint and region explicitly.

## New configuration

```env
STORAGE_DRIVER=s3
S3_ENDPOINT=https://...
S3_REGION=eu-central-1
S3_BUCKET=meleo-verification-private
S3_ACCESS_KEY_ID=...
S3_SECRET_ACCESS_KEY=...
SIGNED_DOCUMENT_URL_TTL_SECONDS=120
```

The bucket must be private. Do not enable anonymous/public read access.

## Existing v5.2 local documents

If verification files already exist from v5.2, keep the old `VERIFICATION_STORAGE_DIR` available temporarily, configure the S3 variables and run `npm run storage:migrate`. The migration uploads the already-encrypted bytes and updates only the database `storage_key`. Take a database/files backup first.

## Existing v5.2 local documents

If a deployment already contains verification files from v5.2, keep the old `VERIFICATION_STORAGE_DIR` mounted temporarily, configure the new S3 variables, and run:

```bash
npm run storage:migrate
```

The migration uploads the already-encrypted bytes and updates each database `storage_key`; it does not decrypt/re-encrypt the source file. Take a database/files backup before running it.
